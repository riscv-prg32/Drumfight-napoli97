# Publishing on the PRG32 Cartridge Store

Release 1.1.0 ships one Store bundle:

| Bundle | Store id | Contents |
|---|---|---|
| `dist/drumfight-napoli97-1.1.0-store.zip` | `org.riscv-prg32.drumfight-napoli97` | `manifest.json`, `icon.png`, `splash.png`, `drumfight-napoli97-esp32c6.prg32`, `drumfight-napoli97-qemu.prg32` |

It was validated with CartridgeStore's own ingestion code
(`_prepare_bundle()`, the implementation of `POST /api/publish/bundle`, at
commit `212e060`) and is **ready for submission**. It has **not** been
submitted: publishing is an authenticated, human-approved step. Checksums
are in `dist/SHA256SUMS`.

## Bundle format (CartridgeStore `docs/api.md`, "Bundle Publish")

```text
manifest.json     prg32-metadata-1.0 object + assets + architectures + colophon
icon.png          64x64 palettised PNG (251 bytes)
splash.png        320x200 gameplay frame from the QEMU firmware (the Store's screenshot slot)
*.prg32           one file per architecture: esp32c6 and qemu
```

The manifest is generated by `scripts/pack-store-bundle.sh` from
`metadata/metadata.json` and `metadata/colophon.json`:

- `abi` must be `prg32-metadata-1.0` (the Store rejects anything else);
- `runtime` is removed (the Store writes `runtime.architecture` per variant);
- `assets` = `{"icon": "icon.png", "splash": "splash.png"}`;
- `architectures` = the `esp32c6` and `qemu` files;
- `colophon` is embedded as an object.

The Store rebuilds every cartridge from the manifest, icon, splash and
colophon. The rebuilt images are about 54.4 KB, within the 64 KiB cartridge
slot (about 11.1 KB free); 24.8 KB of that is the drum kit.

The 30-second preview (`assets/store/preview.mp4`) is repository media and
is not part of the bundle.

## Pack and validate

```bash
scripts/build.sh
```

```bash
scripts/pack-store-bundle.sh
```

Expected, with the Store's ingestion code available (see
[reproduce.md](reproduce.md), step 6):

```text
esp32c6  drumfight-napoli97-esp32c6.prg32    54392 bytes (+11144 free) OK [store-ingest]
qemu     drumfight-napoli97-qemu.prg32       54390 bytes (+11146 free) OK [store-ingest]
drumfight-napoli97-1.1.0-store.zip: READY for submission (store-ingest)
```

Without the CartridgeStore checkout the validator falls back to structural
checks (`[structural]`); with the checkout but without its Python
requirements, to its format module (`[store-format]`).

## Before submitting

- [ ] `tests/run_tests.sh`: all suites pass
- [ ] `scripts/build.sh`: both cartridges, budgets respected, position independence proven
- [ ] `scripts/check_hosts.sh`: PRG32-QT and QEMU pass
- [ ] `scripts/pack-store-bundle.sh`: `READY for submission (store-ingest)`
- [ ] `cd dist && shasum -a 256 -c SHA256SUMS`
- [ ] hardware acceptance on an ESP32-C6 recorded ([testing.md](testing.md))
- [ ] metadata reviewed by the project owner: Store id, authors, license, description
- [ ] human approval of the release

## Submitting (authenticated, human-controlled)

No script in this repository contacts a Store and no credentials are stored
here. A maintainer with a Store account creates a personal Bearer token in
the Store (`/auth/tokens`) and submits the bundle from the PRG32 checkout:

```bash
python3 -m prg32 store publish-bundle ../Drumfight-napoli97/dist/drumfight-napoli97-1.1.0-store.zip --store-url https://store.prg32.uniparthenope.it/ --token "$PRG32_STORE_TOKEN"
```

or with curl:

```bash
curl -X POST https://store.prg32.uniparthenope.it/api/publish/bundle -H "Authorization: Bearer $PRG32_STORE_TOKEN" -F bundle=@dist/drumfight-napoli97-1.1.0-store.zip
```

The Store answers `{"status": "pending", "review_required": true, ...}`.
The cartridge appears in the catalog only after an editor verifies the
submission. Editors may adjust descriptive fields.

## Releasing a new version

1. Bump `version` (and `updated_at`, `release_date`) in
   `metadata/metadata.json` and `metadata/colophon.json`, and add an entry
   to `CHANGELOG.md`.
2. If the pattern format, the snapshot layout, the judge or the moves
   changed, bump the multiplayer signature in both places
   ([multiplayer.md](multiplayer.md)).
3. Re-run the checklist above; the bundle is named after the version.
4. Update the numbers in the documentation (budgets, checksums are
   regenerated; expected outputs in [reproduce.md](reproduce.md) and
   [testing.md](testing.md)).
